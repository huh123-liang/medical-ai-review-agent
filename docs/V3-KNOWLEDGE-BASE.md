# v3 rubric knowledge base and local hybrid retrieval (step 2)

## Contents of `kb/v3`

| File | What | Source | Scored? |
|---|---|---|---|
| `profile-platform-6d.json` (v0.2) | 6 platform dimensions, 1–5 anchors | Dimension names/descriptions: platform `scripts/domain.mjs`. Anchor wording adapted by the project from HealthBench axes (Arora et al. 2025), Ayers et al. 2023 (JAMA Intern Med, 5-point quality scale), Singhal et al. 2023 (Nature, clinician axes), QUEST (Tam et al. 2024, npj Digit Med) | defines the scale |

| `situations-healthbench.jsonl` | 17 situations (HealthBench theme × situation) with an `applies_when` text | HealthBench taxonomy; `applies_when` wording by project | — |
| `healthbench-items.jsonl` | 30 HealthBench consensus criteria linked to their situations; 1 source defect corrected (hedging/no-uncertainty step 2 polarity) | HealthBench (MIT License, openai/simple-evals); dimension mapping by project | yes, when the situation applies |
| `disease-items.jsonl` | 2 disease reference notes (metformin and eGFR, FDA 2016; hypertensive emergency, Merck Manual 2025) | guidelines, paraphrased | **no** – reference only until a named reviewer approves (decision 2026-10-25) |

`healthbench-*.jsonl` are generated by `scripts/build_kb_v3_healthbench.py` from the public HealthBench file
(only criterion text + category are read); `--check` verifies the committed files. Nothing in the KB has been
clinically reviewed; the profile says so and reports carry `clinical_validation: NOT_VALIDATED`.

## Three levels

* **General**: mandatory items (always) and situational HealthBench criteria (only in their situation).
* **Disease**: selected by the case's disease tags (`CaseMeta.diseases`), never by similarity; reference only.
* **Case**: bound to one `case_id`.

## Retrieval (`src/medical_jury/v3/hybrid.py`)

* Local stack: SQLite FTS5 (BM25) + Chroma persistent collection + `BAAI/bge-small-en-v1.5` ONNX loaded from
  `.cache/fastembed` with `local_files_only` (no download at run time) + reciprocal rank fusion.
* Index: `data/v3-index/<kb>-<config>/` with `manifest.json` (KB hash, model files hash, tokenizer, document
  fields), written last; a mismatching or partial index is refused, never silently reused.
* Query: conversation only; the answer under review and the reviewer task text never enter it.
* Mandatory items are never displaced by retrieved items; at most one situation per exclusive group.

### Which situations are applied

The step-2 evaluation (`reports/retrieval-v3-20261025T133001Z-ce3be8/REPORT.md`) showed that similarity
retrieval picks the correct HealthBench situation for 11.7 % of dev-B conversations — the same as always
predicting the most common situation (11.2 %). A supervised kNN router reached 28 %. Situations are clinical
judgments, not topics, and a wrong situation can invert a verdict. Therefore:

| `situation_policy` | Applied situations | Use |
|---|---|---|
| `metadata` (default) | those named in `CaseMeta.situations`; none otherwise | production and validation |
| `llm` | metadata situations if given; otherwise the LLM router's choice (step 3) | once the router is measured on dev |
| `retrieved` | top hybrid-ranked situation | experiments only; labelled in the trace |

The hybrid ranking is always recorded as `suggested_situations` so it can be audited, and the LLM router
(`src/medical_jury/v3/router.py`, measured with `scripts/eval_situation_router_v3.py`) is compared against it on
the same gold labels and the same dev-A / dev-B split.

## Rebuilding / extending

* New criteria: add lines to an `*items*.jsonl` file with a real `source`; disease items stay `reference` until
  `approved_by` names a reviewer. The KB hash changes, so a new index is built automatically on next use.
* New situations: add to a `situations*.jsonl` file; every situation needs at least one linked item.
* Changing the embedding model: put its files under `.cache/fastembed` on the machine (it is never downloaded
  by the agent), change `EMBEDDING_MODEL` in `scripts/run_review_v3.py`, and rerun the retrieval evaluation.
