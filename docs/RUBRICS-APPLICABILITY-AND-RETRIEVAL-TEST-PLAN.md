# 第2步方案：Rubrics适用性与检索测试

状态：设计方案，尚未建立跨病例临床通用库，尚未执行本方案的正式检索基准。制定日期：2026-10-24。现有MVP2保持不动。

## 1. 为什么不能直接把100条现有记录当作通用知识库

现有Chroma+BGE索引确实可检索，但100条记录主要是开发集病例绑定准则。原医生针对某个对话认可的准则，不等于已经认可其跨疾病、跨患者复用。当前 `approved=true` 表示本地允许使用原病例准则，不能解释为临床专家批准通用性。

当前代码只强制检查病例ID、task_type、approved及dev索引边界；`applicability` 是说明文本，疾病、年龄、地域、时效和照护阶段尚未成为可执行过滤条件。因此下面内容是下一版本要实施的契约，而不是当前已有能力。

## 2. 三类资料必须分开

| 类型 | 回答的问题 | 用途及限制 |
| --- | --- | --- |
| Rubrics | 这次应该评判什么？ | 决定必检项、任务/疾病/病例准则；不根据被评回答删除不利准则 |
| 医学事实/安全来源 | 哪项临床主张有依据？ | 独立来源、适用人群和版本；不能把准则文本当成完整医学事实库 |
| 医生标签 | 这个固定回答是否满足准则？ | 只用于离线meta-evaluation，不进入查询、提示词、向量索引或Agent工具 |

本轮新增的幼儿乘车进食规则是窄范围风险筛查，不是已完成的医学事实检索系统。

## 3. 准则记录契约（待实施v2）

保留旧ID和历史快照，新增版本不得覆盖已经使用的记录。建议字段：

| 字段 | 含义/使用规则 |
| --- | --- |
| rubric_id / version / supersedes | 不可变身份、版本和前驱关系 |
| layer | general、disease_task、case；兼容当前general/task/case需显式迁移映射 |
| criterion_text / polarity / weight | 准则原文、met的语义、权重；负向准则不能默认“met就是好” |
| mandatory / mandatory_scope | 哪类任务的必检项；不是仅凭向量相似度决定必检 |
| task_kinds / clinical_domains | 任务类型、疾病/领域；多病共存可组合，不凭关键词自动确认诊断 |
| case_id / group_id | 病例层必须绑定；其他层不得通过复制病例答案变成通用规则 |
| population / age_range / care_setting / care_stage | 人群、年龄、场景与照护阶段；未知信息保留unknown，不猜测为满足 |
| jurisdictions / input_languages | 地域/指南适用范围、支持输入语言；与准则文本语言分开 |
| inclusion / exclusion | 可执行条件与排除条件；条件结构而不是仅一段自由文本 |
| source_url / source_version / locator / license | 来源、版本、位置、使用许可；缺许可须确认，不因公开可下载就自动可再分发 |
| valid_from / valid_to / review_due | 时效和复核期限；指南有更新不能继续默认为永久有效 |
| approval_status / reviewed_by / reviewed_at | draft、pending_review、approved、deprecated；通用适用性需单独审核 |
| split / origin_group_ids | 开发索引与样本血缘；防止验证/测试病例准则、答案或标签进入开发库 |

设计示例：`examples/proposed-rubric-v2.json`。它是草案，不可直接导入当前正式索引。

## 4. 计划检索流程

输入病例的结构化元数据与上下文
→ 校验任务、数据版本和准则库快照
→ 硬性适用性过滤（病例、任务、人群、地域、批准状态、时效、语言）
→ 必检准则直载
→ 对剩余可选准则做本地BGE+Chroma检索
→ 程序去重/检查冲突，合并必检项
→ 冻结选中准则及选择理由
→ 单Jury逐项判断、证据校验、风险门控、计分与审计。

规则：

- 当前 `case.task + context` 查询继续排除 `candidate_output`，避免回答选择自己的考题。临床元数据若用模型抽取，必须有出处和unknown分支，不能把模型猜测当硬过滤事实。
- 不能跨病例兜底。没有适用准则返回 `NoApplicableRubric`，暂不调用付费裁判，不制造“0分”或自动补标准。
- 必检项覆盖不受top-k限制；超过运行条数上限时显式拒绝或分批计划，不静默丢弃。
- 可选检索需排除已直载的必检ID，避免必检项占满近邻槽位后导致可选项不足。现有代码需要专项测试此边界。
- 相互冲突、过期或适用性未知的准则进入人工审核；不让LLM自行放宽适用范围。
- 开发索引、冻结版本和实验查询要有hash；向量距离不是批准、适用性或医学真实性证明。

## 5. 按阶段建设测试集

### A：离线契约/权限测试，建议至少40个合成场景

覆盖跨患者、跨组、错误任务、未批准、已废弃、过期、年龄缺失/边界、地域冲突、语言不支持、多病共存、无适用项、重复ID、必检项超额、可选项被必检项挤占、Prompt injection、被评回答诱导选准则、验证/测试记录试图入库。合成样例只证明程序约束，不报告医学检索准确率。

### B：原病例绑定链路测试

在新的隔离测试collection中使用现有开发病例准则，验证真实本地Embedding与Chroma过滤、去重、必检直载、稳定来源和索引血缘。它只证明“已知病例的正确记录能否找回”，不能当跨病例泛化。

### C：跨病例准则适用性金标准

建议先人工整理20–30条候选可复用准则、30–50个开发查询（仅是拟定规模）。每个查询记录：已确认适用必检集合、可选相关集合、不适用集合及原因；unknown不得默认为相关。至少覆盖改写、急性就医建议、慢病随访、用药问答、多病共存与地域差异。

先由研究人员做任务适用性审核；涉及临床正确性、人群/指南冲突的条目必须标为待临床专家确认。没有医生参与时明确称“研究员审核集”，不能声称医生金标准。只做去标识化公共/合成材料，不接医院患者数据。

在C之前，不把当前100条病例绑定记录自动批量提升为通用规则。保留来源原文、抽象出的候选规则及修改理由，分别审核。

### D：冻结后正式对照

开发集确认流程后冻结元数据契约、候选库、Embedding、top-k、过滤器、阈值、Prompt和门控版本。再一次性使用独立验证集做两条链路：

1. Oracle：人工确认的适用准则直接供给裁判。
2. Retrieval：同一病例自动选准则后交同一个裁判。

先测准则选择，再测相同准则上的判断。漏检准则必须计入覆盖失败，不能只比较“成功找到的容易条目”；额外不适用准则单独计误选。若验证结果用于修改方法，该验证集即成为开发证据，下一次需新的未见验证集。隐藏测试集留到方案最终冻结。

## 6. 指标与预设门槛（目标，不是实测成绩）

| 指标 | 计算口径 | 初始目标/硬限制 |
| --- | --- | --- |
| Mandatory coverage | 找回必检数/应检必检数，另报全覆盖查询占比 | 100%，不得被top-k挤掉 |
| Wrong-case / unapproved / expired leakage | 误选此类记录数与受影响查询数 | 0；违反即阻止进入正式库 |
| Optional Recall@4 | 每查询找回的相关可选数/应有相关可选数，报告macro和micro | 暂定macro ≥0.90，需随任务重新确认 |
| Precision@4 | 每查询选中相关可选数/实际选中可选数 | 报告实测，不用高召回掩盖误选 |
| MRR | 首个相关可选项倒数排名均值 | 仅对存在相关可选项的查询计算 |
| Empty / unknown / conflict rate | 无适用、适用性未知、冲突查询/总查询 | 分开报告，不将unknown转0或成功 |
| Jury agreement / Kappa | 对原始医生二分类标签逐人比较，按病例组估计区间 | 研究指标，不自动转成1–5分MAE/Spearman |
| Safety escape / gate workload | 已审核危险建议漏过门控数、被标复核比例 | 没有独立安全标注时不报敏感度/特异度 |
| Coverage / latency / cost | 所有计划条目含失败；记录P50/P95与累计费用 | 全部留痕；总预算不超过30元 |

没有相关可选项时Recall/MRR为不适用，不记0；没有选中但应选时Recall为0、Precision不定义。若选择全部候选，可能召回高但精度低，不能称检索成功。建议top-k仅在开发集比较2/4/8，选定后不在验证集反复挑参数。

## 7. 未来平台和多Agent边界

保持 `Node后端 → 独立Jury服务 → Admin`。未来报告新增 rubric_selection、applicability_trace、knowledge_snapshot、safety_screen、release_status；医生人工评分与Jury记录独立，不覆盖锁定结果、不向Doctor暴露他人分数。API字段变更先做版本兼容测试。

检索、规则过滤和验证模块目前是确定性模块，不称为多个Agent。未来确有收益后才考虑分离Retriever/Verifier，复用任务ID、快照、可取消接口、预算和审计；不能因为拆成Agent就扩大其网络、文件或数据权限。

## 8. 本轮交付与停止点

本轮只交付本方案和草案契约，不运行C/D、不批量改造现有索引、不读医院数据、不修改平台。进入实施前需确认候选准则审核人、临床争议复核渠道、拟定任务范围与单轮费用上限。当前结果不足以保证替代医生。
