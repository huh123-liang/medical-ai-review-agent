# 第 2 阶段：情境路由 v1 vs v2（PROTOCOL-V3-ROUTER-V2）

版本 `router-v2-compare-1`，预注册日期 2026-10-27，在任何付费调用之前写定。属于开发证据，不是临床结论。

## 1. 背景：第 6 步的路由错误分析

第 6 步中路由的准确率是 0.70（105/150），45 条选错。错误分布（`rag-ablation-v3-20261026T051555Z-20d325/routes.jsonl`，离线分析，没有新增调用）：

| 正确情境 → 路由选择 | 条数 |
|---|---|
| context_seeking：信息足够 → 信息不足 | 12 |
| hedging：没有不确定性 → 可减少的不确定性 | 10 |
| health_data_tasks：信息足够完成任务 → 信息不足 | 5 |
| emergency_referrals：紧急 / 不紧急 → 视情况紧急 | 3 |
| 其他 | 15 |

- **27/45 的错误是同一个方向**：路由选了「信息不足 / 有不确定性 / 可能紧急」这类更保守的选项，而医生的情境标注是「已经够用 / 有明确答案」。
- 选错的例子多是能直接回答的问题，例如：轻度脚踝扭伤两天后能否开始拉伸；成人 CPR 比例；改写一段已经写明「没有更多细节」的病史。
- 路由给出的置信度区分对错的能力有限：答对时平均 0.90，答错时平均 0.83。

**情境定义也有问题。** KB 里的情境定义（`applies_when`）是项目自己写的。例如「信息足够」被写成「给出了症状、病程、严重程度、年龄和病史」，比 HealthBench 实际的标准严得多，模型自然容易偏向「信息不足」。

## 2. 改动：`v3-situation-router-2`

- **系统提示**：在 v1 基础上增加一段判断原则：「更多细节总能让回答更精确，但仅此一点不构成信息缺失、不确定或可能紧急；只有当缺失或不确定会实质改变正确答案、或使安全回答无法给出时，才选这类选项」，并要求结合整段对话判断。
- **每组的判断方法**：新文件 `kb/router/decision-tests-v2.json`，覆盖 context_seeking、hedging、health_data_tasks、emergency_referrals 四组。v2 的输入中，这四组会附带 `decision_test`。
- **保持不变的部分**：
  - KB 本身（情境、准则文件和它们的哈希）不改，检索索引也不受影响。
  - v1 提示词逐字不变：哈希 `18ea42b0…` 已在测试中固定；按第 6 步的 150 条对话重新构造 v1 消息，哈希全部吻合。
- **输入范围**：路由只看到对话本身，看不到被审回答、准则、医生标签或正确情境。

**已知风险**：判断方法是看了第 6 步的错误之后写的。因此不能在那 150 组上评估 v2，只能用从未使用过的新组。

## 3. 设计

- **样本**：从未使用过的 HealthBench dev 组中抽 150 组，每组 1 条；按组均匀抽样，保持自然的主题比例；种子 20261029。排除所有已用过的组（`used_dev_groups_v3`，包括 `router-v3b-*` 本身）。目前可用的新组约 1198 个。
- **配对**：同一条对话分别用 v1 和 v2 各路由一次，共 300 次调用，按条目交替排列，使中途中断时两个版本完成得一样多。
- **调用设置**：DeepSeek V4 Pro，温度 0，JSON 模式，每次最多 600 个输出 token。
- **正确答案**：HealthBench 的类别元数据（该对话所属情境）。只在打分阶段、路由结果封存之后才读取；全程不使用医生的逐条标签。
- **计分**：路由失败或选「none」都算错，和实际运行时一样（这种情况下不会套用任何情境准则）。

## 4. 主要终点与采用规则（预注册）

- **主要指标**：准确率，即在正确情境所属的组里选中正确情境的比例。
- **满足以下两条，才采用 v2**：
  1. v2 准确率高于 v1，且精确 McNemar 检验（双侧）p < 0.05；
  2. v2 的宏平均召回率（只算样本中至少 3 条的正确情境）≥ v1 的宏平均召回率 − 0.02。这一条用来防止 v2 只是把偏向从「信息不足」翻到「信息足够」：在偏斜的样本上，这样准确率也会上升。
- 不满足时保留 v1，结果照实报告。

## 5. 次要指标（只报告，不决定采用与否）

- 两版本准确率之差的 bootstrap 95% CI；
- 按组的准确率；
- 每个情境的召回率和混淆矩阵；
- 置信度区分对错的能力（AUROC）；
- 失败数。

## 6. 中断处理

- 如果 401/402/403/429 或预算耗尽导致中断，可以用 `complete` 阶段把被技术性中断的调用补跑一次，只能补一次（有哨兵文件）。
- 补跑的记录标记为 `completed_later`。
- 模型输出本身失败的（格式错误等）不补跑，按错计。

## 7. 本阶段不做的事

- 不测端到端的评分一致性（κ）。如果 v2 被采用，路由选对的条目和「给定正确准则」时的结果完全相同（第 6 步已验证），所以端到端效果可以在下一步只对路由选错的条目补评。
- 不做「置信度低时退回整套准则」的混合策略，因为现在置信度区分对错的能力不够。等 v2 结果出来再决定。

## 8. 成本与停止条件

- **费用**：
  - 计划阶段打印的上界约 48.7 元。按 UTF-8 字节数计 token，并预留输出上限，所以偏保守。
  - 按第 6 步的实际花费（150 次 v1 路由约 5.1 元）估算，本次实际约 11–12 元。
  - 执行时需要 `--run-limit 50`，才能通过「上界 ≤ 单次限额」的检查；账本只按实际用量扣费。
- **停止条件**：401/402/403/429 或预算耗尽立即停止；连续 3 次失败停止；前 50 次中失败超过 5 次停止；不自动重试。

## 9. 运行命令（在设备上）

```
.venv\Scripts\python scripts/run_router_v2.py route --judge deepseek-pro --run-limit 50                 # 先看计划
.venv\Scripts\python scripts/run_router_v2.py route --judge deepseek-pro --run-limit 50 --authorized    # 确认后执行
.venv\Scripts\python scripts/run_router_v2.py score --run-dir reports/router-v3b-<...>                  # 打分，不调用模型
```

## 10. 结果（2026-10-27 运行，2026-11-11 打分）

运行目录 `reports/router-v3b-20261027T153438Z-ca939a`，300 次调用，299 次完成，1 次输出不合规（v2，按错计），没有中断。

| 指标 | v1 | v2 |
|---|---|---|
| 准确率（150 条） | 0.753 | 0.740 |
| 宏平均召回率 | 0.728 | 0.737 |
| 置信度区分对错的能力（AUROC） | 0.66 | 0.73 |

- 差值 −0.013，95% CI [−0.087, 0.060]；只有 v1 对 18 条，只有 v2 对 16 条；精确 McNemar p = 0.86。
- **按预注册规则：不采用 v2，保留 v1。**
- **v2 只是把错误换了方向**：
  - context_seeking：「信息足够」的召回从 7/15 升到 11/15，「信息不足」从 9/9 降到 4/9；
  - health_data_tasks：「足够」从 4/7 升到 7/7，「不足」从 7/12 降到 3/12；
  - hedging：「没有不确定性」从 3/8 升到 6/8，「可减少的不确定性」从 12/13 降到 7/13。
- **解读**：这几组情境的边界本身就模糊，靠改写提示词只能挪动偏向，不能提高总体准确率。要求路由在互斥情境里硬选一个，这个设计本身就是瓶颈，后续应改为不依赖硬选的做法（例如同时套用候选情境的准则，由每条准则自带的前提决定是否适用）。
- **费用**：按用量估算约 11.2 元；打分在本地完成，没有新增调用。
