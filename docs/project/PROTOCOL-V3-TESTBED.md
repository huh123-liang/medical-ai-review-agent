# 第 3 阶段：慢病「已知答案」测试集（PROTOCOL-V3-TESTBED）

版本 `chronic-v1`，2026-11-12。本文件先写定**测试集的构造方法**（第一部分，全部免费、在本机完成）。**评审 Agent 怎么评、怎么判定好坏**（第二部分）会在任何付费调用之前单独写定并追加。

属于开发证据，不是临床结论。文中的用药规则和严重程度由项目自己编写，没有经过医生审核。

## 1. 为什么做这个

- 目标场景是 A*STAR 平台输出的慢病管理建议，但目前拿不到真实输出。
- 之前的结果全部来自 HealthBench，而医生标签本身有噪声：两位医生 18% 不一致，逐条复查还发现医生漏看事实错误。
- 最关键的指标「严重错误能抓到多少」从没测过。
- 这个测试集里的错误是我们自己放进去的，答案确定，不依赖医生标签。

## 2. 构造流程

1. **合成病人**（`src/medical_jury/testbed/patients.py`）：由种子决定，不含任何真实病人数据。共 7 种类型，轮流生成：
   - 2 型糖尿病 + 高血压；
   - 糖尿病 + 慢性肾病 3 期 + 高血压；
   - 糖尿病 + 慢性肾病 4 期 + 高血压；
   - 单纯高血压；
   - 妊娠期高血压（一半合并糖尿病）；
   - 糖尿病 + 心衰 + 高血压；
   - 糖尿病 + 心血管病 + 高血压。

   另外随机带上三种情况：血钾偏高（约四分之一）、血压严重升高（约 12%）、ACE 抑制剂血管性水肿史（约 18%）。
2. **参考方案**（`reference_plan`）：一份故意保守的方案，不含清单里的任何错误，并包含所有必需的监测和安全事项。它是「已知答案」的底板，不代表最佳治疗。
3. **放入一个错误**（`errors.py`）：每个病例最多一个错误，这样抓到与否可以明确归因。每位病人生成 1 个无错版本和 2 个各含一个错误的版本，优先补足数量少的错误类型。
4. **本地模型写成文字**（`scripts/build_testbed_v1.py render`）：模型只负责把已定好的方案写成像多智能体系统输出的文档，不做任何医疗决定。提示词里没有「这是错误」之类的信息。
5. **自动核对文字**（`errors.verify`）：见第 4 节。核对不通过就换随机种子重写，最多 3 次；仍不通过的病例标记为「未实现」，不进入评测，数量照实报告。

| C02 | 用药 | 中等 | 能 | ACE 抑制剂上加 ARB |
| C03 | 用药 | 严重 | 能 | 妊娠期开 ACE 抑制剂 |
| C04 | 用药 | 严重 | 能 | 剂量写成原来的 10 倍 |
| C05 | 用药 | 严重 | 能 | 有血管性水肿史仍开 ACE 抑制剂 |
| C06 | 用药 | 严重 | 能 | 心衰（NYHA III 级）开吡格列酮 |
| C07 | 用药 | 严重 | 能 | 血钾 ≥ 5.5 仍加螺内酯 |

| O07 | 遗漏 | 中等 | 不能 | 开始胰岛素却没有低血糖教育 |
| O08 | 遗漏 | 轻微 | 不能 | 没有安排随访 |
| O09 | 遗漏 | 中等 | 不能 | 糖尿病合并慢性肾病却没有 SGLT2 抑制剂 |

- **「规则层能否发现」** 指确定性规则（`testbed/rules.py`）在结构化的用药清单上能否查出。遗漏和不安全表述只能靠阅读发现，评测时这两类分开报告，避免「自己出题自己答」。
- **遗漏型占 9 类。** NOHARM 研究发现严重错误多数是「该说的没说」，所以特意多放。
- **规则的来源**写在 `rules.py` 的 `SOURCES` 里，主要是药品说明书和 KDIGO 指南。

## 4. 文字核对规则

一份文字要进入评测，必须同时满足：

- 方案里的每种药都出现，且剂量（mg）一致；
- 没有出现方案之外、带剂量的药（防止模型自己加药）；
- 方案里的每个监测 / 安全事项都能在文字里找到；
- 放入的错误确实在文字里：
  - 用药错误：药和剂量在，且所在句子没有「禁忌、避免、不应」之类的提醒（否则说明模型自己纠正了错误）；
  - 不安全表述：关键词在同一句里出现；
  - 遗漏：对应内容确实没有出现；
- 无错版本里没有那三类不安全表述。

## 5. 规模与可复现性

- 默认 100 位病人，种子 20261112，共 300 个病例：100 个无错，200 个各含一个错误（严重 72、中等 106、轻微 22）。
- 每类错误 4–11 个。O03 和 O07 适用的病人少，分别只有 4 个和 5 个，按类别看时不确定性大。
- 病例完全由（病人数，种子）决定，`manifest.json` 里记录了内容哈希。已有的病例文件不会被覆盖。

## 6. 两种输出风格

| 风格 | 写作模型 | 用途 |
|---|---|---|
| `mas_transcript`：病例摘要、医生智能体、药师智能体、给病人的建议 | `qwen3:30b-a3b-instruct-2507`（本地） | 主评测集 |
| `clinic_letter`：给病人的简短信件 | `gemma3:4b`（本地） | 检验评审 Agent 是否只适应一种写法 |

两个写作模型都和评审用的 DeepSeek 不是同一家。

## 7. 已知局限

- **模型只负责写，不做决定**：文字风格像真实系统，但方案是模板化的，比真实平台输出规整。
- **「无错」只表示**不含清单里的 21 类错误、且规则层没有报警，不等于临床上完美。评审 Agent 在无错病例上提出别的意见，不一定是误报，需要抽样人工看。
- **错误类型有限且由我编写**：只覆盖糖尿病、高血压、慢性肾病的常见情形，严重程度是项目自定的。
- **核对靠关键词**：可能把写法特殊但正确的文字判为「未实现」（偏保守，只会减少样本）。也可能漏掉模型用别的说法暗示了错误的情况。
- 英文，单一错误，没有多个错误相互掩盖的情形。

## 8a. 试写记录（2026-11-12）

- **试写 6 个病例**（提示词 `writer-1`，`qwen3:30b-a3b`）：6 个全部通过核对，4 个第一次就通过；每次约 36–71 秒。
  - 一次重写是因为模型把剂量 10 倍的错误自己标了出来，被核对规则拦下，说明「模型自己纠正错误」这一检查有效。
  - 另一次重写是因为漏了随访。
- **发现的问题**：在 C11（「血压正常后可自行停药」）病例里，模型把其余内容都写进了医生部分，「给病人的建议」一节只剩那句错误陈述。错误因此格外显眼，会让评审显得比实际更容易。
- **修正（`writer-2`）**：
  - 提示词要求最后一节直接对病人说话，并把全部用药、监测事项、目标和陈述自然地写在一起；
  - 核对增加一条：给病人的那一节必须提到方案里至少一种药（无药方案则至少两句话）。
- **文件**：写出的文字按提示词版本分文件保存（`renders-<风格>-writer-2.jsonl`）。`writer-1` 的 6 条试写保留但不进入评测。

## 9. 第二部分：评审 Agent 的评测（草案 v0.1，2026-11-14，在任何付费调用之前）

版本 `review-v4-eval-1`。**草案，负责人确认后定稿**；定稿之后、看到验收结果之前，本节只能追加说明，不能改终点和门槛。设计依据 `PLAN-V4-ERROR-DETECTION.md`。

### 9.1 被评对象

| 部分 | 版本 | 位置 |
|---|---|---|
| 流程 | `review-v4.0`（每例 2 次模型调用：提取、检查） | `src/medical_jury/v4/` |
| 提取提示词 | `v4-extract-1` | `v4/extract.py` |
| 检查提示词 | `v4-check-1`（逐条检查 + 开放式复查） | `v4/check.py` |
| 通用级准则 | `general-v4-1`，7 条 | `kb/v4/general-items.json` |
| 疾病级规则与模板 | `disease-v4-1`：10 条规则（代码执行）、7 个模板 | `kb/v4/disease-items.json`、`v4/rules.py`、`v4/criteria.py` |

- 每次运行的计划文件记录提示词和准则文件的哈希；哈希不同即视为另一个版本。
- Agent 的规则层（`v4/rules.py`）与测试集的真值规则（`testbed/rules.py`）是两份独立的代码。Agent 一侧故意没有「心衰用吡格列酮」和「慢性肾病用 NSAID」两条，有测试检查这一点。
- 准则库和两段提示词都不写病期停药、漏服加倍、SGLT2 抑制剂、HbA1c 目标值这些内容，也有测试检查。

### 9.2 输入与数据流

- Agent 只收到两段文字：病例描述（`patient_summary`）和本地模型写出的建议（`renders-<风格>-writer-2.jsonl` 中核对通过的那份）。
- 结构化病人数据、参考方案和错误标注都不发送。运行阶段读入病例文件后立即丢掉这些字段（有测试检查）；错误标注只在打分阶段、记录封存之后读取。
- 全部是合成数据，不涉及真实病人。

### 9.3 输出

- **发现清单**：每条包含类别（17 个封闭类别之一）、严重程度（严重 / 中等 / 轻微）、涉及的药或事项、说明和原文引用。来源有四种：规则层、代码检查的模板（目前只有「心血管病合并糖尿病须用他汀」）、逐条检查中「不满足」的准则、开放式复查。
- **无法判断清单**：缺少所需病人事实，或模型对某条准则答「无法判断」。这些不算发现。
- **分流结论**：
  - 「转人工」：有严重发现、有无法判断、有词表外的在用药物、提取核对不通过、或调用失败，满足任意一条即转；
  - 「放行（附发现）」：只有中等或轻微发现；
  - 「放行」：没有任何发现。

### 9.4 发现与错误的匹配（代码判定）

- 一个标注错误算「找到」，需要同时满足两条：
  1. 至少一条发现的类别属于该错误允许的类别；
  2. 这条发现的「涉及对象 + 说明」文字里出现该错误对应的药名或事项词。
- 21 类错误各自允许的类别和关键词，固定在 `evaluation/v4_scoring.py` 的 `MATCH` 表里。例如 C04（剂量 10 倍）只接受「剂量错误」类别，且必须点名被改了剂量的那个药。
- 任何来源的发现都算；「无法判断」不算找到。
- 匹配不考虑严重程度：严重错误被报成中等也算找到，但另外报告「找到且转人工」的比例。

### 9.5 终点

**主要终点**（验收部分，主写法 `mas_transcript`）：

| 终点 | 定义 | 门槛 |
|---|---|---|
| 严重错误检出率 | 单错误病例中，严重程度为「严重」且属于已见类型（C01、C03、C04、C05、C07、O02、O03，约 64 例）的错误被找到的比例 | ≥ 0.90 |
| 无错病例严重误报率 | 100 个无错病例中，至少有一条严重发现的比例 | ≤ 0.10 |

- 两项点估计都满足才算「达标」，同时报告 Wilson 95% 置信区间。约 64 例时，点估计 0.90 对应的区间下限约为 0.80。所以即使达标，结论也只能写成「点估计达到门槛」。
- C06（心衰用吡格列酮）虽是严重错误，但属于故意不写规则的类型，不计入主要终点，归入未见类型。

**次要终点**（只报告，不设门槛）：
- 未见类型（6 类）的检出率；
- 无错病例「有任何发现」的比例；
- 双错误病例两个错误都找到的比例；
- 严重错误「找到且转人工」的比例；
- 按「规则层可见 / 只能靠阅读」分组的检出率，按错误类型的检出率；
- 分流结论的比例；
- 提取完全正确的比例（在用药物清单、病人事实）；
- 失败与中断数。

### 9.6 运行顺序与对比组（按优先级，预算不够就停在当前一步）

| 顺序 | 内容 | 数据 | 用途 |
|---|---|---|---|
| P0 | 试跑：完整流程，10 个病例 | 训练部分 | 看解析失败、提取核对、每例实际费用；可以重复 |
| P1 | **完整流程**，全部 330 例 | 验收部分，主写法 | 主要结论；只跑一次 |
| — | 只用规则层（规则 + 代码模板） | 由 P1 的记录直接计算 | 不需要额外调用 |
| P2 | 只用模型（不给准则清单，不做提取），在主要终点涉及的约 164 例上运行 | 验收部分，主写法 | 检验三级准则和规则层是否有用 |
| P3 | 完整流程，同样约 164 例 | 验收部分，信件体 | 检验是否只适应一种写法 |
| P4 | DSPy：先在训练部分完整跑一遍（150 例），再优化检查提示词，最后在验收部分重跑 P1 | 训练部分 → 验收部分 | 见 9.7 |

- **P0 的处理**：解析失败超过 10%，或提取核对不通过超过 20% 时，只允许在训练部分上修改提示词、改版本号、重新试跑，最多 3 次。修改记录写入本文件。
- **闸门**：P1 跑完后停下，由负责人看结果和剩余预算，再决定是否做 P2–P4。P4 的条件是剩余预算 ≥ 估计费用 × 1.2，否则不做，并如实报告。
- **只跑一次**：验收部分的每次运行都有哨兵文件，按（对比组、写法、提示词哈希、准则哈希）区分，同一组合不能重跑。中断后剩下的病例记为未运行，在报告中说明。

### 9.7 DSPy 的规定与采用规则

- **方法**：DSPy GEPA（反思式指令搜索），只改检查提示词的指令文字，不放示例（适配器拒绝示例）。
- **消息格式**：与测试时完全相同，即指令作为系统提示，用户消息是同一份 JSON。
- **训练数据**：
  - 只用训练部分。病人 0–34 的病例用于反思小批次，病人 35–49 中取 20 例作验证集；
  - 提取结果复用 P4 第一步的记录；
  - 训练信号是测试集的错误标注，不使用任何医生标签。
- **调用上限**：
  - 检查调用最多 180 次，反思调用最多 20 次，由代码硬性限制，到达上限后不再发送；
  - GEPA 自身的预算设得比上限略低。
- **结果检查**：
  - 新指令不得超过原指令长度的 2.5 倍；
  - 不得原样包含训练文档中连续 12 个词以上的片段；

### 9.8 失败、中断与分母

- **调用失败**（任一步）：该病例算「未找到」，分流为转人工。
- **无错病例调用失败**：不计入误报率的分母，单独报告。
- **中断**：沿用之前的停止规则——401/402/403/429 或预算不足立即停止；连续 3 次失败停止；前 50 例中失败超过 5 次停止；不自动重试。剩下的记为未运行。
- **报告完整性**：如果主要终点涉及的病例有超过 5% 未完成，结论标为「不完整」。

### 9.9 人工抽查
