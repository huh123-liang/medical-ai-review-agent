# 第 1 阶段：有统计保证的自动判定 预注册（PROTOCOL-V3-SELECTIVE）

制定日期：2026-10-26。本协议在**任何第 1 阶段付费运行之前**写定。运行开始后不再修改；若要修改，必须升版本号、写明理由，并且修改前的结果只能作为开发证据。

## 1. 要回答的问题

对应 `INTENDED-USE.md` 中 L2 等级的核心机制：

> 评分 Agent 能否只在「置信度达到阈值」的样本上自动给出结论，其余转给医生，并且在统计上保证：自动判定的那部分里，与医生共识相反的比例不超过 α？

方法采用 Learn-then-Test 的固定顺序检验，配合精确的 Clopper–Pearson 上界。这套做法在 LLM 评委上的应用见 Jung 等人的 *Trust or Escalate*（ICLR 2025）。实现见 `src/medical_jury/evaluation/selective.py` 和 `scripts/run_selective_v3.py`。

**适用范围**：评分 Agent 拿到的是**正确情境的准则**，与第 6 步的上限组相同。路由选错带来的误差不在本阶段处理，留给第 2 阶段。数据是公开的 HealthBench，不是目标场景。

## 2. 数据

- **来源**：HealthBench meta-evaluation 的 dev 集。用 `natural_sample` 抽 **410 个对话组，每组 1 条**，种子 `20261027`，抽样过程不看标签。
- **排除**：此前所有付费运行用过、或读过标签的组，包括 dev-v2、旧数据库和评审材料、第 6 步消融，见 `src/medical_jury/v3/used_groups.py`。
- **切分**：按对话组哈希切分，不看标签：
  - 试跑 10 组：只用来检查温度采样有没有效果，**不读标签，不计入任何结果**；
  - 校准 200 组：用来选阈值；
  - 测试 200 组：只用一次，用来检验保证是否成立。

## 3. 被评系统与置信度

- **评分 Agent**：DeepSeek V4 Pro，提示词 `v3-dimension-2`，二元判定档案，每条样本检查一条准则，输出上限 800 个 token。
- **每条样本判断 K = 3 次**：
  - 第 0 次：temperature 0，也就是实际部署时的设置；
  - 第 1、2 次：temperature 0.7。
- **主要置信度：自洽度**。三次判断中，与多数结论一致的比例（调用失败的那次也算进分母），再用这几次判断自报置信度的平均值细分同票的情况（实现为 `selective.vote`）。最终结论取多数结论。
- **次要置信度：自报置信度**。只看第 0 次判断给出的置信度，结论也取第 0 次的结论。
- **试跑判定规则**（试跑前写定）：
  - 试跑的 10 组里，如果至少 20% 的样本在三次判断间输出不同，就认为温度采样有效；
  - 否则主要置信度改用自报置信度，并且正式运行只判断 1 次（K = 1）。

## 4. 「错误」的定义

- **主要：与共识相反。**只有在所有医生意见一致，而 Agent 的结论与他们相反时，才记为错误。医生意见不一致的样本没有共识可违背，不算错误；这类样本的数量单独报告。
- **次要：与每位医生分别比较的平均不一致率。**它的下限受医生之间分歧的制约。
- **调用失败的样本**：一律视为转给医生，永远不进入自动判定，但仍计入覆盖率的分母。

## 5. 校准与检验

1. **校准**：在校准集上，把阈值从严到宽依次检验。
   - 每个阈值下，计算自动判定那部分的错误数，以及 Clopper–Pearson 的 (1−δ) 上界；
   - 上界 ≤ α 才通过；**一旦不通过就停止**。最终取通过的最宽阈值；
   - 自动判定样本少于 30 个的阈值直接跳过、不检验。是否跳过只取决于置信度，与标签无关，所以不影响保证的有效性。
2. **参数**：
   - δ = 0.10；
   - α：**主要为 0.05**，次要为 0.10；
   - 主要设定 = 自洽度 + 与共识相反的错误 + α = 0.05。
3. **检验**：把校准得到的阈值原样用在测试集上，只算一次。报告：
   - 自动判定的覆盖率；
   - 实际错误率、上界，以及与每位医生比较的平均不一致率；
   - 「保证是否成立」= 测试集的实际错误率 ≤ α。

   这是一次实现，按设计有 δ 的概率不成立。
4. **其他报告项**：用 AUROC 衡量置信度区分对错的能力；测试集上的「覆盖率–错误率」曲线；两种置信度在相同 α 下的覆盖率对比。

## 6. 运行前已知的情况（只作参考，不作证据）

- **第 6 步上限组**：150 条，标签已经读过，属于样本内结果。
  - 只看自报置信度时，阈值 0.95 覆盖 88%，132 条中有 3 条错误，上界 0.0498，刚好低于 0.05；
  - 整体与共识相反的比例为 5.3%。
- **dev200（v2 提示词）**：整体错误率 15%，在任何阈值下都达不到 α = 0.05。
- **结论**：自报置信度只有 4–5 个取值，太粗，难以在新数据上稳定达到 α = 0.05。这正是引入自洽度的原因。这些数字来自已经看过的数据，**不能拿来证明任何事**。

## 8. 不声称的事

- 结果只适用于「给定正确准则、HealthBench 公开对话」这个设定，不代表平台慢病场景，也不代表整个流程（包括路由）。
- 「与共识一致」不等于临床正确；共识来自 2 位以上医生，样本本身也有局限。
- 即使保证在测试集上成立，也只说明在 L2 等级所需证据中，**这一项在代理数据上可行**。

## 9. 结果（2026-10-26，运行完成后补记，上面各节没有改动）

运行目录：`reports/selective-v3-20261026T062630Z-392497`（报告见其中的 `REPORT.md`）。

- **主要设定（自洽度、α = 0.05）没有达到**：校准集上没有任何阈值通过，自动判定覆盖率为 0。
- **次要设定（α = 0.10）**：两种置信度都在校准集上全覆盖通过，但测试集错误率分别为 10.6% 和 11.1%，**保证没有成立**。
- **基础错误率**：校准集 5.5%，测试集 11.0%。
- **自洽度区分对错的能力**：AUROC 0.70，高于自报置信度的 0.63；但三次判断完全一致的样本里，错误率仍有 6.9%。
- **花费**：约 38 元（含试跑）。

## 10. 修订版 v2：固定分流规则的确认性检验（2026-10-27，在 v2 任何付费运行之前写定）

### 10.1 为什么修订
v1（第 1–9 节）的结论是：只靠置信度阈值，达不到 α = 0.05。v1 的 400 条样本，加上第 6 步上限组的 150 条，**都已经读过标签**，因此只能作为开发数据，用来定下面这条分流规则。规则一旦写定就不再修改，再在**全新的数据**上检验一次。

### 10.2 用来定规则的开发数据（已经看过）

两批数据按主题合并后的错误率：

| 主题 | 条数 | 错误 | 错误率 |
|---|---|---|---|
| hedging | 115 | 2 | 1.7% |
| communication | 125 | 8 | 6.4% |
| context_seeking | 71 | 5 | 7.0% |
| global_health | 114 | 9 | 7.9% |
| emergency_referrals | 63 | 8 | 12.7% |
| health_data_tasks | 56 | 9 | 16.1% |

v1 中三次判断完全一致的样本里：communication 1/76、hedging 1/76 判错。

### 10.3 预先写定的规则（v2）
- **自动判定的条件（同时满足）**：
  1. 准则所属主题是 **communication 或 hedging**；
  2. **K = 3** 次判断全部成功：第 0 次 temperature 0，第 1、2 次 temperature 0.7；
  3. **三次的结论完全一致**。
- **其余一律转医生**：其他主题、三次结论有分歧、或有任何一次调用失败。
- 结论取三次一致的那个结论。评分 Agent、提示词、准则（给定正确情境）都与 v1 相同。

### 10.4 数据
- 来源：HealthBench dev，只在这两个主题中按对话组抽取。用 `natural_sample` 抽 **250 组，每组 1 条**，种子 `20261028`，抽样不看标签。
- 排除：所有用过的组，包括 v1 的 410 组，见 `used_dev_groups_v3`。
- 全部用作测试集，**没有校准环节**，因为规则已经固定，不需要再定阈值。不做试跑：temperature 采样有效已在 v1 中确认。

### 10.5 检验与判定
- **主要指标**：在被自动判定的样本里，与医生共识相反的错误数 k 和样本数 n。计算 Clopper–Pearson 的 (1 − δ) 上界，δ = 0.10。
- **成功的标准**：上界 ≤ α = 0.05。成功就说明，以 90% 的把握，这条规则下自动判定的错误率不超过 5%。
- **覆盖率**分两个口径报告：
  - 在这两个主题内，被自动判定的比例；
  - 换算到全部 dev 对话组的比例：乘以这两个主题占全部对话组的比例，约 0.395。
- **次要指标**：
  - 只按主题分流、只用第 0 次判断时的错误率和上界；
  - 被转给医生的那部分，如果当时自动判定了，会有多少错误；
  - 自动判定部分与每位医生的平均不一致率；
  - 按主题拆分的结果。

### 10.6 费用
- 750 次调用（250 条 × 3），预期约 23 元；
- 分 3 批，每批费用上限约 43 元；
- 每批都会先出计划，经负责人批准后才执行；
- v2 的付费运行只能有一次，第一批开始时会写入一次性哨兵。

### 10.7 不声称的事
- 即使成功，结论也只适用于「HealthBench、这两个主题、给定正确准则」这个设定。
- 平台的慢病准则需要用自己的数据和医生标注，重新逐类证明。

### 10.8 v2 结果（2026-10-27，按实际跑完的部分补记）

运行目录：`reports/selective-v3-20261027T060805Z-394327`（报告见其中的 `REPORT.md`）。

- **运行中断**：服务商返回 HTTP 402（账户余额不足），触发立即停止。750 次调用中完成 439 次，其余 305 次未运行；103 条样本一次都没有评，按规则视为转医生。
- **主要结果**：自动判定 138 条，与医生共识相反 4 条，错误率 2.9%；90% 置信上界 5.7% > 5%，**按预注册标准没有达到**。主要原因是运行中断后样本量不足。
- **次要结果**：只按主题分流、只用第 0 次判断时，错误率 4.8%，上界 7.9%。
- 如果之后补跑这 103 条，必须同时报告「实际跑完的结果」和「补全后的结果」，并写明：补跑的决定是在看到中间结果之后才做的。

### 10.9 修订 v2.1：补跑因技术中断而没有运行的调用（2026-10-27，在补跑之前写定）

- **原因**：v2 的中断来自服务商账户余额不足（HTTP 402），不是模型的输出问题，也不是看了结果之后主动停下的。负责人已为账户充值。
- **补跑哪些**：只补跑「因技术原因没有得到回答」的调用，即：
  - 未运行（NotRun）；
  - 或以立即停止码失败，包括 401、402、403、429、预算不足。

  模型输出格式错误等失败**不补跑**。按 v2 的数据，共 311 次调用（305 次未运行 + 6 次 402），涉及 104 条样本。
- **怎么补跑**：规则、样本、K、temperature、提示词、模型全部与 v2 相同；只补一次，第一次付费补跑时写入一次性哨兵；补跑的结果单独封存在 `completion/` 下。
- **报告**：两种口径都报告，都按同样的标准（上界 ≤ 5%）判定：
  - **实际跑完的结果**（第 10.8 节，没有达到）；
  - **补全后的结果**。
- **必须写明的偏差风险**：补跑的决定是在看到「错误率 2.9%、上界 5.7%，差一点达标」之后才做的。这属于在看到中间结果后决定继续收集数据，会抬高「最终达标」的可能。所以：
  - 补全后的结果**只能作为辅助证据**；
  - 是否最终认定这条规则有效，还需要在下一批全新的数据上再检验一次。
- **代码**：`scripts/run_selective_v3.py complete`。打分阶段发现有补跑结果时，会同时输出 `as_run` 和 `completed` 两种口径。
- **已修复的问题**：打分时，未运行样本的占位记录没有「第几次判断」字段，会被误排到第 0 次的位置。现在改为从调用编号中读取顺序。v2 已有的结果重新计算后完全不变。

### 10.10 补全后的结果（2026-10-27）

- 311 次补跑全部完成；v2 合计 750/750 次完成，花费约 23.0 元。
- **补全后**：自动判定 234 条（主题内 93.6%），错误 11 条，错误率 4.7%，90% 置信上界 7.0% > 5%，**没有达到**。
- **按主题**：communication 7/122，hedging 4/112。
- **错误方向**：11 条中有 9 条是 Agent 判得比医生更严。
- **结论**：按准则类型分流的规则，在新数据上不能提供 5% 的保证。看到中间结果后才补跑这一偏差，并没有把结果推向成功（补跑部分本身的错误率更高）。
- **对目标设定的反思**：α = 0.05 没有以医生之间的表现为参照，后续应先测出单个医生相对于共识的错误率，再定目标。
