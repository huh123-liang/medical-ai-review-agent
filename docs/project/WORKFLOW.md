# 端到端工作流程

## A. 使用公开基准做方法验证

1. 从官方地址下载原始HealthBench meta-evaluation，保存来源、版本、SHA256和上游元信息。
2. 校验字段、标签类型、医生ID与评分数量；不补造不合法标签。
3. 按规范化对话/重复组划分dev、validation、test；输入与医生标签分别落盘。
4. 开发只用dev；测试前冻结样本、输入、原准则、Prompt、模型、费率、token上限与停止规则。
5. Oracle测试直接提供准则；RAG测试独立测准则选择，不混成一个成绩。
6. Agent只读固定上下文、回答、准则和批准来源；不读医生评分。
7. 每次真实调用前预留费用；超时、HTTP错误、截断或未知usage均留痕。
8. 程序检查输出、坐标、条目覆盖；不将格式通过等同于医学正确。
9. 封存所有预测，包括失败、未定、未运行；然后独立评分器读取原医生标签。
10. 逐医生比较，报告完整分母、Macro-F1/Kappa、条件性与整批指标、分歧、费用和局限。完成后先反思，再审批下一步。

## B. 单条合成输入离线使用

`examples/synthetic-request.json` → `evaluate --provider mock` → 本地报告。只证明流程，不输出医生一致性结论。

## C. 将来接入原平台

Admin批准的数据/固定回答 → 平台后端调用独立Agent → 版本化结果 → Admin复核。人工医生标签和Jury结果独立存储，不相互覆盖，不向普通Doctor暴露他人评价。当前未实现平台接线。

## 数据落盘边界

本地`data/public`保存官方原始文件；`data/prepared`保存无标签输入；`data/private`隔离公开医生标签/诊断；`data/vector`保存衍生索引；`data/jury.sqlite`保存任务、准则与费用；`reports`保存运行输出。它们全部不提交Git。

模型不拥有shell、任意网络、文件系统或标签查询工具。输入中的指令、来源和示例只是待审数据；提示词规则本身不是完备的注入抵抗证明。
