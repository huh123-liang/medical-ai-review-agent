# 下一步任务与审批门

原则：更深入而非更大；每部分完成后核对目标、架构、证据与费用，再批准下一部分。不因为仓库公开就自动扩大权限或继续收费。

## P0：先修可靠输出与判分边界

1. 精简三态候选：短ID引用、减少重复哈希/原文、限定每条证据数量；不能只把token上限一味加大。
2. 针对真实原始输出离线复现基线6条证据超限及候选截断，保留失败，不补造截断JSON。
3. 逐条检查分歧：任务是否识别错、原准则边界是否有争议、是否真正存在医学反证。研究意见不成为医生标签。
4. 先离线开发验证；原7例保持未决。完成后单独申请小额新样本实测，旧validation被用于修改方法后不能再称未见测试。

## P1：事实依据、准则适用性与示例记忆

- Rubrics库、医学事实来源库、已审核示例库逻辑分开；SQLite运行日志不是自动学习记忆。
- 需要来源版本、人群/地区/时间/剂型、许可、适用/排除条件及审核状态；不能凭向量相似度判断医疗真伪。
- 必检项直载，病例专属准则不跨病例，缺失/冲突条件不猜测。
- Oracle裁判、检索选择、端到端性能分测。临床标准/来源冲突由独立专业审核确认。

## P2：更严谨的验证与优化

- 扩充来源可核查、按对话/患者血缘隔离的开发与独立验证；可探索MORQA的多维医生评分，不擅自把序数标签阈值化。
- 输出覆盖率、复核率、混淆矩阵、逐主题表现和组级区间，不只看一个总体百分比。
- 有稳定基线和有效标签后再考虑ICL、DSPy/TextGrad；候选只可修改批准的Prompt/示例，不能改测试标签、原患者回答或准则。
- 保留原始测试一次性验收，避免边看结果边改标准。

## P3：平台、多Agent和本地部署

独立服务经版本化接口接原平台；人评分、Jury判断和复核分别存储。必要时拆分Evaluator/Retriever/Verifier，先验证收益，再规划最小权限、人工确认、取消/Kill Switch、预算与全链路审计。

MCP只是工具连接协议，不会自动提高医学准确率。本地模型（如Prometheus）需独立资源/许可/质量验证；“程序跑在本机”不等于“模型已经本地化”。

## 进入下一阶段前必须回答

哪个可观测问题得到解决？原任务/准则是否被不当改变？是否使用独立证据？新增权限与费用是否获批？失败/未定是否完整保留？是否有回归？与原平台边界是否保持？本轮到底证明了什么、没证明什么？
