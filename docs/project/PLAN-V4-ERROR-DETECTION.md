# 调整方案 v4：慢病管理建议的错误检测 Agent

版本 0.1（草案），2026-11-14。**这是给负责人审阅的设计方案，不是预注册协议。**确认后，评测部分会另行写定（追加到 `PROTOCOL-V3-TESTBED.md` 第二部分），然后才会有付费调用。

文中的用药规则、严重程度和验收门槛都由项目自拟，没有经过医生审核。

## 1. 为什么调整

| 之前的做法 | 遇到的问题 |
|---|---|
| 给任意医疗回答打分，用 HealthBench 的医生标签验证 | 医生之间 18% 不一致，还会漏看事实错误；在这种标签上既证明不了、也优化不动 |
| 让模型判断「该用哪条准则」（情境路由） | 准确率卡在 0.75，改提示词只是换一种偏向 |
| 三级准则 | 疾病级只有 2 条，且不计分 |
| DSPy | 没有合规的训练信号（医生标签不能用），一直没跑过 |

## 2. 新定位与边界

**做什么**：输入一份慢病管理建议和病例描述，输出一张「发现清单」和「放行 / 转人工」的结论。发现清单每条包含错误内容、原文引用、严重程度和所依据的准则。

**本阶段的目标等级是 L1（初筛辅助）**，不是自动放行。能够负责任地声称的是：「在已知答案测试集上，严重错误的检出率是多少、误报率是多少」。

| 边界 | 规定 |
|---|---|
| 病种 | 2 型糖尿病、高血压、慢性肾病（含妊娠、心衰等合并情况） |
| 语言 | 英文 |
| 药物 | 只对词表内的药执行规则；**词表外的药一律标记「无法核对」并转人工** |
| 严重发现 | 一律转人工，系统不自行放行 |
| 不做 | 情境路由、多模型陪审团、通用医疗问答评分、替代医生的任何声称 |
| 数据 | 本阶段只用合成病例，不涉及真实病人数据 |

## 3. 三级准则

| 级别 | 回答的问题 | 内容 | 检查方式 |
|---|---|---|---|
| 通用级 | 任何建议都该做到什么 | 约 10 条，每条只管一件事。例：不给危险的自行调药指示；该紧急就医时明确提示；剂量和频次写清楚 | 模型逐条检查 |
| 疾病级 | 这个病、这类药的硬规则 | ① 用药规则（禁忌、剂量上限、重复用药）；② 必备事项模板（如开始 ACE 抑制剂后复查血钾和肌酐） | ① 代码；② 模型 |
| 病例级 | 对这位病人必须有什么、不能有什么 | 由代码把疾病级模板套上病人事实生成。例：「血钾 6.1 → 必须建议紧急处理」 | 模型逐条检查 |

- **哪些准则适用，由病人事实决定，用代码判断**，不再让模型选择。
- 每条准则记录来源（说明书或指南）和「未经医生审核」的状态。
- 混合检索保留，用于为每条发现找指南原文作为依据，不参与决定用哪条准则。

## 4. 流程

```
病例描述 + 建议原文
 ⓪ 提取病人事实（模型，带原文引用）：诊断、eGFR、血钾、血压、妊娠、过敏、心衰分级
 ① 提取建议内容（模型，带原文引用）：每种药的名称、剂量、频次、状态（开始/继续/停用/避免），
    以及监测事项、目标、对病人的指示
 ② 提取核对（代码）：引用能否在原文找到；原文里出现的词表药名是否都被提取；剂量与正则结果是否一致
 ③ 规则层（代码）：禁忌、剂量、重复用药；只对「开始/继续」的药执行
 ④ 生成适用准则清单（代码）：通用级 + 病例级
 ⑤ 逐条检查（模型）：每条准则「满足 / 不满足 / 无法判断」+ 引用
 ⑥ 开放式复查（模型）：清单之外还有没有可能造成伤害的问题
 ⑦ 汇总（代码）：发现清单 + 严重程度
 ⑧ 分流（代码）：出现严重发现、「无法判断」、词表外药物或提取核对不通过 → 转人工
 → 报告（沿用现有 JSON + HTML）
```

模型负责 ⓪①⑤⑥，其余是代码。⓪① 合并为一次调用，⑤⑥ 合并为一次调用，每个病例共 2 次调用。

## 5. DSPy 的位置

| 模块 | 优化什么 | 标准答案 |
|---|---|---|
| 提取（⓪①） | 病人事实和用药清单与真值一致 | 测试集的病人数据和结构化方案 |
| 检查（⑤⑥） | 抓到放入的错误，且无错病例不误报严重问题 | 测试集的错误标注 |

规定：
- 只优化指令文字，不往提示词里放示例；
- 训练信号只来自测试集的训练部分，**不使用任何医生标签**；
- 优化后的提示词先冻结并记录哈希，再在验收部分只跑一次；
- 只有验收部分的主要指标变好才采用，否则保留手写提示词，结果照实报告；
- 优化的调用次数事先封顶。

## 6. 测试集需要先升级到 v2

全量生成还没有跑，所以现在改不浪费任何东西。改动都来自第 9 节自查发现的漏洞：

| 改动 | 原因 |
|---|---|
| 病人数从 100 增加到 150（约 450 个病例） | 验收部分的严重错误数量要够 |
| 按病人划分：50 人训练，100 人验收 | DSPy 不能见到验收病例 |
| 不安全表述类错误每类准备 4 种说法，训练和验收各用 2 种 | 现在每类只有一句固定的话，优化器只要记住这句话就能「抓到」 |
| 指定 4 类错误为「未见类型」：准则库和规则层里故意不写对应条目，训练部分也不出现 | 检验对没写进准则的错误还能抓到多少 |
| Agent 的规则层与测试集的规则模块分开，Agent 的规则故意少两条 | 否则是同一段代码自己出题自己答 |
| 加入「反例」：无错病例里加入「避免使用 NSAID」这类提到药名但不是处方的句子 | 检验会不会把「避免用某药」误当成「开了某药」 |
| 加入 30 个含两个错误的病例，只放在验收部分 | 真实输出可能同时有多个错误，要看会不会顾此失彼 |
| 另一种写法（信件体）只用于验收 | 检验是否只适应了一种格式 |
| 给 Agent 的输入只有病例描述文字，不给结构化数据 | 真实平台输出不会附带结构化病人数据 |

「未见类型」定为：C10（HbA1c 目标过低）、C12（漏服后加倍）、O06（没有病期停药提醒）、O09（没有 SGLT2 抑制剂）。Agent 规则层故意不包含：C06（心衰用吡格列酮）、C08（慢性肾病用 NSAID）。这 6 类在看到任何结果之前就定下。

## 7. 评测与验收（提议值）

| 指标 | 定义 | 提议门槛 |
|---|---|---|
| **严重错误检出率（主要）** | 验收部分、已见类型、严重程度为「严重」的病例中，发现清单里有对应条目的比例 | ≥ 0.90，并报告 95% 置信区间 |
| **无错病例的严重误报率（主要）** | 无错病例中被报告了严重发现的比例 | ≤ 0.10 |
| 未见类型的检出率 | 同上，只算 6 个未见类型 | 只报告，不设门槛 |
| 提取准确率 | 用药清单和病人事实与真值完全一致的比例 | 只报告 |
| 分项 | 按「规则层可发现 / 只能靠阅读发现」、按错误类型、按写法分别报告 | 只报告 |
| 转人工比例 | 被转人工的病例占比 | 只报告 |

- 「发现与错误是否对应」用封闭的类别加药名或事项名来匹配，由代码判定，不由模型裁判。
- 无错病例上的严重误报，抽 20 条人工看原文（由 Claude 看，注明非医生），区分「真误报」和「参考方案本身有争议」。
- 对比组：只用规则层；只用模型（不给准则清单）；完整流程；完整流程 + DSPy。

## 9. 自查：发现的漏洞与修正

| # | 漏洞 | 后果 | 修正 |
|---|---|---|---|
| 1 | 病例级准则和测试集的「必备事项」出自同一套模板 | 等于把答案清单发给了考生，检出率虚高 | 设 4 个未见类型，准则库里不写；加开放式复查（⑥）；分开报告 |
| 2 | Agent 的规则层和测试集判定错误用的是同一段代码 | 规则层的「检出率」只是在验证自己 | 两者分开；Agent 的规则故意少两条；这部分结果解读为「提取是否准确」 |
| 3 | 不安全表述每类只有一句固定的话 | DSPy 会学成「看到这句话就报错」 | 每类 4 种说法，训练和验收各用 2 种 |
| 4 | 提取漏掉一种药时，规则层不会报警 | 最危险的失败方式：悄悄放行 | 代码核对词表药名是否都被提取；引用必须能在原文找到；不通过就转人工 |
| 5 | 「避免使用布洛芬」被当成开了布洛芬 | 误报 | 提取时标注状态（开始/继续/停用/避免）；测试集加反例 |
| 6 | 真实平台输出不带结构化病人数据 | 「按病人事实选准则」在真实场景用不了 | 增加病人事实提取（⓪）；缺失的事实 → 「无法判断」→ 转人工；测试时只给文字 |
| 7 | 词表只有 20 种药 | 词表外的药没有规则可查，会被当成没问题 | 词表外药物一律转人工，并报告占比 |
| 8 | 验收样本太少（原方案验收部分只有约 36 个严重错误） | 置信区间太宽，结论站不住 | 病人数加到 150，验收部分约 70 个以上严重错误 |
| 9 | 每个病例只有一个错误 | 不知道多个错误并存时的表现 | 加 30 个双错误病例，只用于验收 |
| 10 | 「无错」病例只是不含清单内的错误 | 误报率可能被高估 | 误报只算「严重」级别；抽 20 条人工查看并注明 |
| 11 | 严重程度是项目自定的 | 主要指标的口径可能被医生推翻 | 明确标注；整理成清单留待医生审阅；所有严重发现都转人工 |
| 12 | 「严重发现一律转人工」意味着自动放行的比例可能很低 | 与「不需要医生」的远期愿景有距离 | 明确本阶段目标是 L1；如实报告转人工比例 |
| 13 | 预算余量小 | 可能做到一半没钱 | 基线之后设闸；调用次数封顶；可以减半规模 |
| 14 | 写作模型（Qwen）与评审模型同源会偏高 | — | 评审用 DeepSeek，不同源；已满足 |
| 15 | 测试集是模板化的，比真实输出规整 | 结果不能直接外推到真实平台 | 写明这一局限；拿到平台样例或公开的专家标注数据（如 NOHARM）后再做外部验证 |

**没有解决、只能如实说明的两点**：第 11 点（没有医生）和第 15 点（没有真实输出）。它们决定了这一阶段的结论只能是「在已知答案测试集上的表现」。
